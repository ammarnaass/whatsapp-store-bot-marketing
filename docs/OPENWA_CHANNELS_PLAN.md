# خطة قنوات الربط الفني: واتساب مع OpenWA

**الإصدار:** 1.0 (معتمد) | **التاريخ:** 3 نوفمبر 2026 | **ترتبط بـ:** PRD v0.3

**مصدر المعلومات التقنية:** ملف README الخاص بمشروع OpenWA (github.com/rmyndharis/OpenWA). ما لم يتضح من README، مثل أسماء كل الأحداث وترويسة توقيع الـ Webhook، موسوم بعبارة **«يُتحقق»** وتتم مراجعته في مرحلة الاختبار الأولى (Spike) من `openapi.json` ووثيقة `docs/06-api-specification.md`.

---

## 1. الهدف

تحديد **كل القنوات التقنية** التي يتواصل بها تطبيقنا (Electron) مع واتساب عبر OpenWA، ودور كل قناة، وكيفية تأمينها وجعلها موثوقة، مع تصميم طبقة تجريد تسمح لاحقاً بإضافة قناة رسمية (WhatsApp Cloud API) دون إعادة كتابة التطبيق.

## 2. ما يوفره OpenWA فعلياً (من README)

| العنصر | التفاصيل |
|---|---|
| المحركان | `whatsapp-web.js` (الافتراضي، متصفح Chromium حقيقي، مخاطر حظر أقل، ذاكرة 300–500 ميغابايت لكل جلسة) و`baileys` (بروتوكول مباشر، مخاطر حظر أعلى، ذاكرة 30–80 ميغابايت). يُختار بمتغير `ENGINE_TYPE` |
| واجهة REST | على `http://localhost:2785/api`، مصادقة بترويسة `X-API-Key`، وتوثيق Swagger على `/api/docs` |
| الجلسات | `POST /api/sessions` للإنشاء، `POST /api/sessions/{id}/start` للتشغيل، `GET /api/sessions/{id}/qr` لرمز QR |
| الإرسال | مثال موثّق: `POST /api/sessions/{id}/messages/send-text` بحقلي `chatId` و`text`، ويدعم أيضاً الوسائط والتفاعلات والتعديل والإرسال الجماعي |
| Webhooks | `POST /api/sessions/{id}/webhooks` بحقول `url` و`events` و`secret` (توقيع HMAC) ومرشحات اختيارية قبل الإرسال (sender, chatId, body, type, isGroup, fromMe, hasMedia…) |
| أحداث معروفة | `message.received`، `session.status`، `message.edited`، `call.received` (غير موثوق على whatsapp-web.js). **يُتحقق** من القائمة الكاملة |
| WebSocket | مسار `/events` يبثّ الأحداث مباشرة، ويقتصر المفتاح المحدود بمحادثات على أحداث محادثاته فقط |
| MCP | `POST /mcp` عند `MCP_ENABLED=true`: 25 أداة قراءة فقط افتراضياً، و51 أداة كاملة عند `MCP_READONLY=false` |
| الإضافات | «Integration Fabric»: إضافات معزولة رسمية (Chatwoot وTypebot) من مستودع OpenWA-plugins، وعُقد n8n المجتمعية، ومجلد `sdk/` في المستودع |
| مفاتيح API | أدوار admin وoperator وviewer، مع تقييد بجلسات (`allowedSessions`) وبمحادثات (`allowedChats`) |
| التحكم بالإرسال | `SEND_PACING_ENABLED` و`SEND_PACING_WARMUP_SCHEDULE` و`SEND_PACING_COLD_DAILY_CAP` وقاطع الفشل المتتالي، و`SIMULATE_TYPING` مفعّل افتراضياً، و`delayBetweenMessages` للإرسال الجماعي |
| البنية | Node.js 22 LTS وNestJS 11 وTypeScript، قاعدة SQLite أو PostgreSQL، تخزين محلي أو S3، كاش Redis اختياري |

**تحذيرات المشروع نفسه التي تؤثر على خطتنا:**

- OpenWA بوابة **غير رسمية**، وخطر تقييد الحساب أو حظره قائم دائماً. يوصي المشروع برقم مخصص يمكن خسارته، لا برقمك الأساسي.
- رسالة أولى لجهة جديدة قد لا تصل رغم نجاح الاستجابة (سياسة واتساب على الخادم، وليست عطلاً في OpenWA).
- بعض الحسابات لا تستطيع ربط جهاز جديد أصلاً بسبب خطوة مفتاح المرور (passkey) التي لا يدعمها أي من المحركين.
- يعتبر المشروع نفسه غير مناسب للبيئات الخاضعة لتنظيم صارم، ويوصي بواجهة Cloud API الرسمية هناك.
- استدعاءات `RATE_LIMIT_*` لحماية الـ API من الإساءة وليست سقفاً لإرسال الرسائل.

## 3. خريطة قنوات الربط

| # | القناة | الاتجاه | الاستخدام عندنا | الأولوية |
|---|---|---|---|---|
| C1 | REST API | تطبيقنا ← OpenWA | إنشاء الجلسات، QR، إرسال الرسائل والوسائط، قراءة الحالة | أساسية (MVP) |
| C2 | Webhooks | OpenWA ← تطبيقنا | استقبال الرسائل والحالات وتحديثات التسليم | أساسية (MVP) |
| C3 | WebSocket `/events` | OpenWA ← تطبيقنا | قناة بديلة أو مكمّلة للأحداث الحية، ومراقبة حالة الجلسة في الواجهة | ثانوية |
| C4 | MCP `/mcp` | وكيل AI ← OpenWA | أدوات قراءة للوكيل (سياق المحادثة) بمفتاح مقيَّد | اختيارية |
| C5 | الإضافات (Integration Fabric) | داخل OpenWA | Chatwoot وTypebot إن احتجنا صندوق وارد أو تدفقات جاهزة | اختيارية |
| C6 | n8n | OpenWA ↔ n8n | أتمتة خارجية للمستخدمين المتقدمين | مستقبلية |
| C7 | قناة رسمية (Cloud API) | تطبيقنا ↔ Meta | بديل أو احتياطي عند الحجم الكبير أو الحاجة التنظيمية | مستقبلية |
| C8 | قناة داخلية (IPC) | الواجهة ↔ Electron Main | أوامر المستخدم وعرض الأحداث دون كشف المفاتيح للواجهة | أساسية |

**قرار:** نعتمد **C1 + C2** كقناتين أساسيتين، و**C3** للمراقبة الحية. القنوات C4–C7 تُضاف خلف الطبقة التجريدية (القسم 4) دون المساس بالتطبيق.

## 4. المعمارية المقترحة

```
┌────────────── Electron ──────────────┐
│ Renderer (React)                      │
│      │ IPC (contextBridge فقط)        │
│      ▼                                │
│ Main process                          │
│  ├─ Business layer (متجر/بوت/حملات)    │
│  ├─ Agent service (وكيل AI)           │
│  ├─ Channel Gateway  ◄── واجهة موحدة   │
│  │     ├─ OpenWAAdapter (C1+C2+C3)    │
│  │     └─ CloudAPIAdapter (مستقبلاً)   │
│  ├─ Webhook receiver (127.0.0.1)      │
│  ├─ Outbound queue (SQLite)           │
│  └─ OpenWA supervisor (Child Process) │
└───────────────┬───────────────────────┘
                │ HTTP/WS على localhost
                ▼
        OpenWA (NestJS) ── whatsapp-web.js / baileys ── WhatsApp
```

### 4.1 طبقة التجريد (Channel Gateway)

واجهة موحدة لا تعرف تفاصيل OpenWA، وكل ما فوقها (المتجر والبوت والوكيل والحملات) يتعامل معها فقط:

```ts
interface WhatsAppChannel {
  startSession(id: string): Promise<void>;
  getQr(id: string): Promise<string>;
  getStatus(id: string): Promise<SessionStatus>;
  sendText(session: string, chatId: string, text: string, opts?: SendOpts): Promise<SendResult>;
  sendMedia(session: string, chatId: string, media: MediaInput, opts?: SendOpts): Promise<SendResult>;
  onEvent(handler: (e: ChannelEvent) => void): void;   // رسالة واردة، حالة تسليم، حالة جلسة
}
```

- `OpenWAAdapter` ينفذها فوق REST وWebhook وWebSocket.
- `CloudAPIAdapter` لاحقاً ينفذها فوق Meta Cloud API، مع التنبيه إلى أن الإرسال خارج نافذة الـ 24 ساعة يتطلب **قوالب رسائل معتمدة**، وهذا يتطلب معالجة في طبقة الأعمال لا في المحول فقط.
- الأحداث تُحوَّل إلى صيغة داخلية موحدة (`ChannelEvent`) قبل أن تصل لأي مكوّن.

### 4.2 تشغيل OpenWA داخل Electron

- OpenWA يعمل **كعملية فرعية** تُدار من Main (تشغيل، إيقاف، إعادة تشغيل عند التعطل، مراقبة الصحة عبر نقطة الفحص الصحي المتوفرة في OpenWA).
- مشروع OpenWA يتطلب **Node.js 22 LTS**، وقد يختلف إصدار Node المضمّن في Electron، لذلك نشحن **ملف Node منفصلاً** مع التطبيق ونشغّل به OpenWA، ولا نشغّله داخل Node الخاص بـ Electron. **يُتحقق** في المرحلة الأولى.
- محرك `whatsapp-web.js` يحتاج Chromium للتشغيل الآلي (headless) منفصلاً عن Chromium الخاص بواجهة Electron؛ يُحسم في المرحلة الأولى هل نشحن Chromium مستقلاً أم نعيد استخدام الموجود. هذا عامل حجم وتوزيع مهم للتطبيق.
- ملف Docker ومكوّن docker-socket-proxy في OpenWA مخصصان للنشر على السيرفرات، ولا نحتاجهما في تطبيق سطح المكتب (لا Docker على جهاز المستخدم).
- الإعدادات تُمرَّر بمتغيرات البيئة عند الإقلاع: منفذ حر ديناميكي، `DATABASE_TYPE=sqlite` لقاعدة OpenWA المستقلة عن قاعدتنا، `ENGINE_TYPE`، وتفعيل `SEND_PACING_ENABLED=true`.

### 4.3 قاعدتا بيانات منفصلتان

لدى OpenWA قاعدة SQLite خاصة به (جلسات، مفاتيح، سجلات Webhook)، ولدينا قاعدة SQLite للتطبيق. نُبقيهما **منفصلتين**، فلا نكتب في قاعدة OpenWA ولا نعتمد على مخططها، ونتعامل معه عبر الـ API فقط. هذا يسهّل ترقيته.

## 5. تصميم كل قناة

### C1: REST (الأوامر الصادرة)

- **المصادقة:** مفتاح admin يُولَّد عند أول إقلاع ويُكتب في ملف بيانات OpenWA؛ يقرؤه Main مرة واحدة ويخزّنه في **التخزين الآمن لنظام التشغيل** (safeStorage في Electron)، ولا يصل للواجهة أبداً.
- **عملاء المفاتيح:** ننشئ عبر `POST /auth/api-keys` مفاتيح منفصلة بأقل صلاحية: مفتاح operator مقيَّد بالجلسات لخدمة الإرسال، ومفتاح viewer لقراءة الحالة، ومفتاح مقيَّد بمحادثات للوكيل عند الحاجة.
- **طابور صادر دائم (SQLite):** كل رسالة تُسجَّل أولاً ثم تُرسَل؛ حالات: pending ← sent ← delivered ← read ← failed. يستأنف بعد إغلاق مفاجئ.
- **التحكم بالمعدل:** نضبط تباطؤ OpenWA (`SEND_PACING_*`) ونطبّق فوقه تباطؤنا الخاص في الطابور (تأخير بين الرسائل، حد يومي لكل رقم وفق عمر الجلسة)، لأن OpenWA نفسه لا يفرض حداً في الدقيقة.
- **إعادة المحاولة:** تراجع أسي (exponential backoff) للأخطاء المؤقتة، وبلا إعادة محاولة تلقائية لأخطاء الرقم غير الصالح.
- **منع التكرار:** معرّف عملية (idempotency key) محلي لكل رسالة حتى لا تُرسل مرتين عند إعادة المحاولة.

### C2: Webhooks (الأحداث الواردة)

- مستقبِل HTTP **على 127.0.0.1 فقط** وبمنفذ ديناميكي، يُسجَّل عنوانه عبر `POST /api/sessions/{id}/webhooks` مع سر عشوائي طويل.
- **التحقق من التوقيع:** نتحقق من توقيع HMAC لكل طلب قبل المعالجة (ترويسة التوقيع وخوارزميتها **يُتحقق** منها من الوثائق). الطلب غير الموقَّع أو القديم يُرفض.
- **الاستجابة السريعة:** نعيد 200 فوراً بعد كتابة الحدث في **جدول أحداث وارد** في SQLite، ثم نعالجه بشكل غير متزامن، لتفادي مهلة الـ Webhook.
- **إزالة التكرار:** بمعرّف الرسالة (message id) لأن الإعادة ممكنة.
- **المرشحات من جهة OpenWA:** نستخدم المرشحات الذكية لتقليل الضجيج (مثلاً تجاهل `fromMe`، أو الاقتصار على الرسائل الخاصة وتجاهل المجموعات إن لم نحتاجها).
- **الأحداث المطلوبة:** رسالة واردة، تغيّر حالة التسليم/القراءة، تغيّر حالة الجلسة (متصل، منقطع، QR جاهز)، تعديل رسالة. القائمة الكاملة **يُتحقق** منها.

### C3: WebSocket `/events`

- نستخدمه لتحديث الواجهة لحظياً (حالة الجلسة، QR الجديد، مؤشر وصول رسالة) دون انتظار دورة Webhook.
- لا يُعتمد عليه كمصدر وحيد للحقيقة؛ الـ Webhook مع الجدول الدائم هو المصدر، والـ WebSocket للعرض.
- إعادة اتصال تلقائية مع تراجع أسي، وتسوية الأحداث الفائتة بعد الانقطاع بسحب الرسائل الأخيرة من `GET /sessions/{id}/messages`.

### C4: MCP للوكيل (اختياري)

- يُفعَّل بـ `MCP_ENABLED=true` وبوضع القراءة فقط (`MCP_READONLY=true`) افتراضياً.
- لا نعطي النموذج أدوات إرسال مباشرة؛ **الإرسال يمر دائماً عبر طبقة الأعمال** وطابورها وحدودها (حدود الخصم والمراجعة البشرية في PRD).
- المفتاح المستخدم لـ MCP: غير admin، مقيَّد بجلسة ومحادثات الوكيل، بلا قيد IP (يرفضه OpenWA مع MCP)، مع ضبط `MCP_RATE_LIMIT_MAX`.
- **توصيتنا:** لا نعتمد على MCP في الإصدار الأول، فطبقة الأعمال عندنا هي التي تنفّذ أدوات الوكيل، وهذا أضمن لحدود الأمان.

### C5: الإضافات وn8n

- **Chatwoot:** بديل جاهز لصندوق الوارد إن رغبنا بتوفير جهد بناء الواجهة؛ لكنه يضيف خدمة منفصلة ثقيلة على جهاز المستخدم، فلا نوصي به لتطبيق سطح مكتب.
- **n8n:** قناة تصدير للمستخدمين المتقدمين (نكشف Webhook صادراً اختيارياً من تطبيقنا) في مرحلة لاحقة.

### C7: القناة الرسمية (Cloud API)

- تُضاف كمحوّل ثانٍ خلف `WhatsAppChannel` عند الحاجة لحجم كبير أو امتثال.
- فروقات يجب تصميمها من الآن: قوالب الرسائل المعتمدة خارج نافذة 24 ساعة، التحقق من رقم Business، رسوم المحادثات، وWebhook من Meta يتطلب عنوان HTTPS عاماً (يلزم نفق أو خادم وسيط خفيف لتطبيق سطح المكتب).
- هذا المسار هو **الاحتياطي الموصى به** للمبيعات الحرجة كما ينصح مشروع OpenWA نفسه.

## 6. مخطط الأحداث إلى نموذج بياناتنا

| حدث OpenWA | الإجراء في تطبيقنا |
|---|---|
| `message.received` | حفظ في `messages`، تحديد المعالج (تدفق/وكيل/موظف)، تشغيله |
| تحديث حالة الرسالة (تسليم/قراءة) | تحديث `messages.status` وإحصاءات الحملة |
| `session.status` | تحديث `sessions.status` وإشعار الواجهة، وتفعيل إعادة الاتصال عند الانقطاع |
| `message.edited` | تحديث نص الرسالة في السجل |
| `call.received` | (إن فُعّل) رد آلي: «لا نستقبل المكالمات، اكتب رسالتك» |

## 7. الأمان

1. كل الاتصال على `127.0.0.1` فقط، ولا يُفتح أي منفذ للشبكة الخارجية.
2. مفتاح admin في التخزين الآمن، ومفاتيح ثانوية بأقل صلاحية ومقيَّدة بجلسات/محادثات.
3. سر الـ Webhook عشوائي طويل ويُدوَّر عند الحاجة.
4. عزل الـ Renderer: `contextIsolation` مفعّل و`nodeIntegration` معطّل، والـ IPC بقائمة أوامر محددة فقط.
5. لوحة OpenWA المدمجة (منفذ 2785) **لا تُكشف للمستخدم النهائي** في الإنتاج، فواجهتنا هي الواجهة الوحيدة.
6. سجل تدقيق لكل إرسال وكل عملية إدارية.
7. تنظيف المرفقات المؤقتة والروابط المؤقتة للتحميل.

## 8. الموثوقية والمراقبة

- **مشرف العملية (Supervisor):** إعادة تشغيل OpenWA تلقائياً عند التعطل مع حد أقصى للمحاولات وتنبيه للمستخدم.
- **فحص صحة دوري** لـ OpenWA ولكل جلسة، وحالات الجلسة (متصل، منقطع، QR جاهز) ظاهرة دائماً في الشريط العلوي.
- **قاطع دائرة (Circuit breaker):** عند فشل متتالٍ في الإرسال يتوقف الطابور تلقائياً ويُنبَّه المالك (وهو سلوك يتسق مع قاطع الفشل في OpenWA).
- **تسوية الأحداث الفائتة** بعد أي انقطاع (إعادة اتصال أو إعادة تشغيل).
- **عدّادات ومؤشرات:** زمن الإرسال، نسبة الفشل، عمق الطابور، تأخر الأحداث الواردة، عدد إعادات الاتصال.
- **سجلات** قابلة للتصدير (بعد إخفاء الأسرار) لتسهيل الدعم.

## 9. سياسة الإرسال الآمن (مستمدة من إرشادات OpenWA)

1. **رقم مخصص** للأتمتة، لا الرقم الأساسي.
2. **تسخين الرقم الجديد:** أيام أولى بسلوك بشري (رسائل قليلة لجهات محفوظة، مجموعة أو اثنتان، صورة ملف شخصي) قبل أي حملة.
3. **لا إرسال بارد** لأرقام لم تتواصل معك أو لم توافق.
4. **تباطؤ الإرسال مفعّل دائماً** (`SEND_PACING_ENABLED=true`) مع حد خاص للمحادثات الجديدة.
5. **محاكاة الكتابة** (`SIMULATE_TYPING`) مفعّلة، وتأخير عشوائي بين الرسائل.
6. **الأولوية للردود** على من بدأ المحادثة، والتنبيهات لمن ينتظرها (تحديثات الطلبات)، والحملات بحدود منخفضة.
7. **انسحاب فوري** عند طلب العميل، وقائمة حظر.
8. **مسار احتياطي** (بريد/SMS/Cloud API) لكل ما هو حرج ماليّاً.
9. اختيار المحرك: `whatsapp-web.js` عند أولوية سلامة الحساب مع قبول استهلاك ذاكرة أعلى، و`baileys` عند الحاجة لجلسات كثيرة بقبول خطر أعلى. ونوصي بـ `whatsapp-web.js` افتراضياً لتطبيق المتجر.

| المرحلة | المدة | المخرجات | معيار القبول |
|---|---|---|---|
| **P0: تجربة جدوى (Spike)** | 1 أسبوع | تشغيل OpenWA كعملية فرعية من Electron؛ إنشاء جلسة، QR، إرسال واستقبال؛ حسم Node وChromium وحجم التوزيع؛ استخراج قائمة الأحداث وترويسة التوقيع من `openapi.json` | رسالة تُرسَل وتُستقبل عبر تطبيق Electron على Windows وmacOS |
| **P1: القناتان الأساسيتان** | 2 أسبوع | `OpenWAAdapter` (C1+C2)، مستقبل Webhook بالتحقق من التوقيع، جدولا الأحداث الوارد والطابور الصادر، مشرف العملية | لا فقدان لرسالة بعد إغلاق مفاجئ، ولا تكرار عند إعادة الإرسال |
| **P2: الأمان والمفاتيح** | 1 أسبوع | التخزين الآمن، مفاتيح مقيَّدة، قفل الواجهة، عزل Renderer | فحص أمني داخلي ناجح، ولا مفتاح في الواجهة أو السجلات |
| **P3: المراقبة والاتصال الحي** | 1 أسبوع | WebSocket `/events`، تسوية الأحداث الفائتة، فحص الصحة، قاطع الدائرة | تعافٍ تلقائي بعد قطع الشبكة أو تعطل OpenWA |
| **P4: سياسة الإرسال الآمن** | 1 أسبوع | تباطؤ مزدوج، تسخين الأرقام، حدود الحملات، الانسحاب | اختبار حملة 500 رسالة بلا تجاوز الحدود |
| **P5: تكامل الوكيل** | 2 أسبوع | أدوات الوكيل عبر طبقة الأعمال (وليس MCP)، تمرير السياق، حدود المراجعة | سيناريوهات الاختبار الأمني للوكيل (PRD القسم 9.8) ناجحة |
| **P6: قنوات اختيارية** | لاحقاً | MCP للقراءة، تصدير n8n، تقييم `CloudAPIAdapter` | حسب الحاجة |

## 11. خطة الاختبار

- **اختبارات الوحدة:** التحقق من توقيع HMAC، إزالة التكرار، منطق الطابور وإعادة المحاولة.
- **اختبارات التكامل:** OpenWA حقيقي مع رقم اختبار: إرسال/استقبال نصوص ووسائط، فصل الشبكة، قتل العملية، إعادة تشغيل.
- **اختبار الحمل:** 1000 رسالة واردة خلال دقائق دون فقدان أو تجمّد الواجهة.
- **اختبار الأمان:** محاولة Webhook مزوَّر، مفتاح مقيَّد يحاول الوصول لمحادثة خارج نطاقه، التأكد أن لوحة OpenWA غير متاحة خارج الجهاز.
- **اختبار توافق المنصات:** Windows 10+ وmacOS 12+ وUbuntu 22.04+.
- **اختبار الترقية:** تحديث إصدار OpenWA المضمّن مع الحفاظ على الجلسات.

## 12. المخاطر

| الخطر | الأثر | التخفيف |
|---|---|---|
| حظر الرقم أو تقييده | توقف المبيعات | رقم مخصص، تسخين، تباطؤ، انسحاب، مسار احتياطي، Cloud API لاحقاً |
| تغيير واتساب البروتوكول فتتعطل المكتبة | توقف الاتصال | عزل OpenWA كوحدة قابلة للتحديث السريع، تثبيت إصدار مختبَر، متابعة مستودع OpenWA |
| تعذر ربط الجهاز بسبب مفتاح المرور | عدم إمكانية إضافة الرقم | تنبيه واضح للمستخدم، وتوصية بتجربة رقم آخر أو القناة الرسمية |
| ضياع الرسالة الأولى لجهة جديدة | عدم وصول رد الوكيل لعميل جديد | نجاح الاستجابة لا يعني التسليم؛ نعتمد حالة التسليم لا استجابة الـ API، ونوفر مساراً بديلاً |
| حجم التوزيع (Node + Chromium) | تطبيق كبير وتثبيت بطيء | حسم الخيارات في P0، وتحميل المكوّنات الثقيلة عند أول تشغيل |
| استهلاك الذاكرة (whatsapp-web.js) | بطء على الأجهزة الضعيفة | حد أدنى موصى للجهاز، وعدد جلسات محدود افتراضياً |
| الامتثال التنظيمي | مخالفة شروط واتساب أو القوانين | إفصاح واضح للمستخدم، إرسال لمن وافق فقط، وCloud API للاستخدامات الحساسة |

## 13. أسئلة تُحسم في P0

1. ما القائمة الكاملة لأحداث الـ Webhook وصيغة حمولة كل حدث؟
2. ما اسم ترويسة توقيع HMAC وخوارزميته وصيغة الحقل الزمني (لمنع الإعادة)؟
3. هل يمكن تشغيل OpenWA بـ Node مستقل داخل حزمة Electron على الأنظمة الثلاثة بلا مشاكل في المكتبات الأصلية (native modules)؟
4. أي خيار أنسب لـ Chromium: شحنه مع التطبيق أم تنزيله عند أول تشغيل؟
5. كيف يتصرف OpenWA عند إعادة التشغيل: هل تُستعاد الجلسات تلقائياً بلا مسح QR جديد؟
6. هل نحتاج بوابة رسمية من البداية لجزء من الأرقام (مثل رقم المبيعات الرئيسي)، وهل نريد الجمع بين القناتين من النسخة الأولى؟
